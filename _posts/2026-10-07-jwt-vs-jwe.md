People say "JWT" and "JWE" like they're rivals. They're not. They answer two different questions, and mixing them up is how secrets end up readable in a browser console.

## The one-minute version

| | Question it answers | Can anyone read the contents? | Can anyone tamper with it? |
|---|---|---|---|
| **JWT** (signed, a.k.a. JWS) | "Is this really from who it claims, and unchanged?" | **Yes** | **No** (signature breaks) |
| **JWE** (encrypted) | "Can only the intended receiver read this?" | **No** | **No** (authenticated encryption) |

**JWT is a *format*** for carrying claims (`sub`, `exp`, `role`…). **JWS and JWE are two ways to *wrap* it**: one signs it, the other encrypts it. When people say "JWT" they almost always mean the signed kind.

## Picture 1: the postcard

A normal JWT is a **postcard with a tamper-proof stamp**.

```
   ┌──────────────────────────────────────────────┐
   │  {"sub": "alice", "role": "admin", "exp": …} │   ← anyone can read this
   │                                              │
   │                      [ SIGNATURE STAMP ✔ ]   │   ← nobody can forge this
   └──────────────────────────────────────────────┘
```

The postman, the neighbour, and anyone sniffing the network can read it. But if they change `"role": "user"` to `"admin"`, the stamp no longer matches and the receiver rejects it.

Try it: paste any JWT into jwt.io. The payload is just Base64URL, **encoded, not encrypted**. Decoding needs no key.

A signed JWT looks like 3 parts:

```
xxxxx.yyyyy.zzzzz
header . payload . signature
```

## Picture 2: the sealed envelope

A JWE is a **locked envelope**. Only the holder of the right key can open it.

```
   ┌──────────────────────────────────────────────┐
   │ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ │   ← contents hidden
   │ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ │
   └──────────────────────────────────────────────┘
```

It has 5 parts:

```
aaaaa.bbbbb.ccccc.ddddd.eeeee
header . encrypted key . IV . ciphertext . auth tag
```

The auth tag also makes tampering detectable, so a JWE gives you secrecy **and** integrity.

## The flow side by side

```
 SIGNED JWT (JWS)                         ENCRYPTED (JWE)

 Auth server                              Auth server
   │ sign with PRIVATE key                  │ encrypt with receiver's PUBLIC key
   ▼                                        ▼
 [ readable payload + signature ]         [ ciphertext only ]
   │                                        │
   ▼                                        ▼
 API verifies with PUBLIC key             API decrypts with its PRIVATE key
 "Authentic ✔  (but not secret)"          "Secret ✔  (and untampered)"
```

Note the key direction flips: **signing uses the sender's private key, encryption uses the receiver's public key.**

## So what is secure?

Short answer: **neither is "secure" by default. Each protects something different.**

| You need… | Use |
|---|---|
| Prove who issued the token and that it wasn't altered | Signed JWT |
| Hide the contents from the client, proxies, or logs | JWE |
| Both authenticity of the issuer *and* secrecy | **Sign first, then encrypt** (a "nested JWT") |

Why sign-then-encrypt? A JWE only proves "someone who knows the receiver's public key made this" and public keys are, well, public. Signing inside proves who the issuer actually is.

### Practical rules

1. **Never put secrets in a signed-only JWT.** No passwords, national IDs, card numbers. Treat the payload as public.
2. **Always verify the signature** and check `exp`, `iss` and `aud`. A decoded token is not a trusted token.
3. **Pin the algorithm** on the server. Reject `alg: none` and don't let the token pick its own algorithm.
4. **Keep lifetimes short** (minutes), and use refresh tokens for longer sessions. A JWT can't be "unsent", so expiry is your seatbelt.
5. **Always use HTTPS.** Neither format replaces transport security.
6. **Prefer not to need JWE.** If the data is sensitive, ask whether it should be in the token at all. Often the better design is a small token holding just an ID, with the real data looked up server-side.
7. **Protect the keys.** Signing keys and decryption keys are the whole game. Rotate them and never ship them to the client.

## The rule of thumb

> **JWT = "I can prove who wrote this."  JWE = "Only you can read this."**
> If the client or anyone in the middle shouldn't see it, it needs encryption, or shouldn't be in the token at all.
